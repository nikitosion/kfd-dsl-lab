# Лабораторная «Свой DSL»

Создайте DSL для проверки HTTP-ответов. Перепишите на нём функции `check01`…`check10` из `lesson09.legacy`, сохранив их поведение. Имена операций DSL выберите сами.

## Исходники

- `app/src/main/kotlin/lesson09/HttpResponse.kt` — модель ответа.
- `app/src/main/kotlin/lesson09/legacy/Checks.kt` — исходные проверки.
- `app/src/test/kotlin/lesson09/LegacySmokeTest.kt` — примеры тестов.

Не изменяйте `HttpResponse.kt` и `legacy/Checks.kt`. Реализацию DSL разместите в пакете `lesson09.dsl`, тесты — в `app/src/test/kotlin/lesson09`.

## Условия проверок

Проверка возвращает `true`, если выполнены все условия её строки. Дополнительные поля и заголовки не влияют на результат.

| Функция | Условия успеха |
|---|---|
| `check01` | Статус от 200 до 299 включительно. |
| `check02` | Статус 204; тело равно `null` или `""`. |
| `check03` | Статус 200; Content-Type начинается с `application/json`; тело не `null` и не пусто. Разбор JSON не выполняется. |
| `check04` | Статус 201; Location начинается с `/users/`. |
| `check05` | Статус 200; Accept содержит значения `application/json` и `text/html`. |
| `check06` | Статус 200; JSON содержит ключ `id`, в том числе со значением `null`; `name` — строка `Иванов`. |
| `check07` | Статус 200; JSON: `id` — число 42, `active` — логическое true. |
| `check08` | Статус 200; JSON: ключ `note` присутствует и равен null, `deleted` — логическое false. |
| `check09` | Статус 422; Content-Type начинается с `application/json`; JSON: `error` — строка `invalid`, `retry` — логическое false. |
| `check10` | Статус 200; X-Trace начинается с `trace-`; JSON: `quote` — строка `он сказал "да"`, `path` — строка `C:\tmp` с одним обратным слешем. |

## Заголовки

Имена сравнивайте без учёта регистра. Если несколько ключей отличаются только регистром, объедините их списки значений.

Каждая операция над заголовком проходит, если ей удовлетворяет хотя бы одно значение. Разные операции могут выполняться на разных значениях: в `check05` нужны два элемента списка.

Значения сравнивайте с учётом регистра, без `trim` и разбиения по запятой. Префикс проверяйте через `startsWith`: например, `application/jsonp` начинается с `application/json`.

При ошибке перечислите фактические значения. Для отсутствующего заголовка укажите «заголовок отсутствует», для пустого списка — «список значений пуст».

## JSON

Напишите разбор JSON в `lesson09/dsl/Json.kt` без внешних библиотек. Поддержите один объект верхнего уровня, включая `{}`. Значения полей: строка, целое число в диапазоне `Long`, `true`, `false`, `null`.

- Запись целого числа: `-?(0|[1-9][0-9]*)`.
- В строках поддерживаются экранирования `\"` и `\\`. Другие escape-последовательности отклоняются.
- Между лексемами допускаются пробел, табуляция, LF и CR. Внутри строк неэкранированные символы U+0000…U+001F запрещены.
- Вложенные объекты, массивы, дроби, переполнение числа, лишняя запятая и посторонний текст после объекта считаются ошибкой.
- При повторении ключа сохраняется последнее значение. Укажите это правило комментарием над функцией разбора.
- Наличие ключа и значение `null` различаются. Число 42 и строка `"42"` тоже различаются.

Если тело не разобрано, добавьте одно расхождение для этого вызова блока `json` с причиной ошибки. Проверки его полей не выполняйте; остальные проверки ответа продолжайте.

## Требования к DSL

1. Разделите операции по типам получателей и пометьте их одним `@DslMarker`. Вложенные блоки должны иметь свои типы: например, `body { json { field("id") { ... } } }`.
2. Неявный вызов внешнего `status { ... }` внутри `body { ... }` должен запрещаться компилятором. Явное обращение через `this@check` остаётся допустимым.
3. Возвращайте sealed-результат или data-класс со списком расхождений. Каждое расхождение содержит путь, ожидание и факт. Не заменяйте результат на `Boolean` и не бросайте исключение при несовпадении данных.
4. Собирайте все независимые расхождения в порядке вызова операций. Одна неудачная операция добавляет одну запись.
5. Для каждого запуска создавайте новый накопитель. Возвращайте копию списка: следующие проверки не должны изменять прежний результат.
6. Не подключайте библиотеки для проверок или разбора JSON. Не используйте `kotlin-reflect` и обход членов классов. Ссылки на функции и свойства допустимы.

## Тесты и сдача

Для каждой из десяти функций добавьте хотя бы один подходящий и один неподходящий ответ. Включите `null` и пустое тело, неверный JSON, отсутствующий заголовок, имя заголовка в другом регистре и несколько значений заголовка.

На каждом ответе сравните результат исходной функции с результатом DSL: `true` соответствует отсутствию расхождений. Отдельно проверьте пути, ожидания и факты при нескольких ошибках.

Добавьте тест повторного вызова одного блока на одном неверном ответе. Результаты должны быть равны, а список первого результата не должен изменяться.

В `docs/wont-compile.kt.txt` сохраните собственный пример запрещённого неявного вызова, команду компиляции, полученную ошибку и объяснение через типы получателей. Укажите package/import и вызывающую функцию. Проверьте также, что явный вызов компилируется.

После занятия 11 выполните пункты A–D по generics в той же ветке. Для варианта с `Class<T>` разрешены `T::class.java`, `Class.isInstance` и `Class.cast`.
