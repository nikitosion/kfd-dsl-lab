# Лабораторная «Свой DSL»

Постройте DSL на лямбдах с получателем. Каждую из десяти функций `lesson09.legacy.check01`…`check10` перепишите на своём языке. Имена операций выбирайте сами. Не изменяйте `HttpResponse.kt` и `legacy/Checks.kt`.

## Исходные материалы

- `app/src/main/kotlin/lesson09/HttpResponse.kt` — модель ответа.
- `app/src/main/kotlin/lesson09/legacy/Checks.kt` — десять функций и закрытые помощники эталона.
- `app/src/test/kotlin/lesson09/LegacySmokeTest.kt` — стартовые примеры тестов. Собственный корпус эквивалентности нужно дополнить для всех десяти проверок.

Пакет `lesson09` позволяет добавить работу рядом с исходниками предыдущих занятий. Создайте пакет `lesson09.dsl` и свой тестовый класс в `lesson09`; импорт модели: `import lesson09.HttpResponse`.

## Контракт десяти проверок

Все перечисленные в строке условия соединены «И». Равенство строк и префиксы чувствительны к регистру; только имена заголовков сравниваются без него. Статус — обычное целое число, без дополнительной валидации модели.

| Функция | Условия успеха |
|---|---|
| `check01` | Статус от 200 до 299 включительно. |
| `check02` | Статус 204; тело отсутствует или равно пустой строке. Пробел не считается пустой строкой. |
| `check03` | Статус 200; Content-Type начинается с `application/json`; тело не `null` и не пусто. Синтаксис JSON здесь не проверяется. |
| `check04` | Статус 201; Location начинается с `/users/`. |
| `check05` | Статус 200; Accept содержит значение `application/json` и значение `text/html`. Это могут быть разные элементы списка. |
| `check06` | Статус 200; тело — поддерживаемый JSON-объект; ключ `id` присутствует, включая значение `null`; `name` — строка `Иванов`. |
| `check07` | Статус 200; JSON: `id` — число 42, `active` — логическое true. |
| `check08` | Статус 200; JSON: ключ `note` присутствует и равен null, `deleted` — логическое false. |
| `check09` | Статус 422; Content-Type начинается с `application/json`; JSON: `error` — строка `invalid`, `retry` — логическое false. |
| `check10` | Статус 200; X-Trace начинается с `trace-`; JSON: `quote` — строка `он сказал "да"`, `path` — строка `C:\tmp` с одним обратным слешем. |

Префикс — буквальная операция `startsWith`: например, `application/jsonp` тоже имеет префикс `application/json`. Дополнительные поля, заголовки и тело там, где оно не проверяется, не влияют на результат.

## Заголовки

Объедините списки всех ключей, равных без учёта регистра. Каждая операция проходит, если ей удовлетворяет хотя бы одно значение. Не склеивайте значения через запятую и не применяйте trim. Пустой список и отсутствующий заголовок дают отказ проверки значения, но разные факты в расхождении: «список значений пуст» и «заголовок отсутствует». Перечисляйте все фактические значения.

## Подмножество JSON

Реализуйте собственный разбор в `lesson09/dsl/Json.kt` без внешних библиотек. Помощники legacy — закрытая часть эталона, не API нового DSL. Допускается один объект верхнего уровня, включая `{}`. Значения: строка, целое Long, true, false, null. Объекты и массивы внутри значений не поддерживаются.

- Целое: `-?(0|[1-9][0-9]*)`, диапазон от −9223372036854775808 до 9223372036854775807.
- В строках обязательны экранирования `\"` и `\\`; прочие escape-последовательности для этого задания отклоняются.
- Между лексемами допускаются только пробел, табуляция, LF и CR. Непроэкранированные символы U+0000…U+001F внутри строк запрещены.
- Лишняя запятая, посторонний хвост, дробь, ведущий плюс, ведущие нули и переполнение числа означают неподдерживаемое тело.
- **Повторяющийся ключ: последнее значение побеждает.** Запишите это правило комментарием над функцией разбора. Здесь оно фиксировано, чтобы результат совпадал с неизменяемым legacy и на таких входах.
- Наличие ключа отличается от ненулевого значения. Число 42 отличается от строки `"42"`.

Ошибка разбора даёт одно расхождение на вызов блока `json`; проверки полей этого блока не выполняются. Другие проверки статуса, заголовков и тела продолжаются. Сообщение содержит причину и позицию (индекс UTF-16 с нуля). Неподдерживаемый вход не должен выбрасывать исключение. Это учебное подмножество, а не полный JSON-парсер.

## Маршрут

1. Добавьте файлы в `app`, выполните `:app:test` и создайте ветку.
2. Выпишите операции из таблицы и распределите их по типам получателей: ответ, статус, заголовок, тело, JSON, поле. Назовите неуместные неявные вызовы.
3. Создайте корпус: для каждой проверки минимум один true и один false. Добавьте null и пустое тело, неверный JSON, отсутствие заголовка, другой регистр и несколько значений. Назовите каждый случай.
4. Объявите API, напишите тест эквивалентности по всем парам legacy/DSL. На компилируемой временной реализации убедитесь, что тест обнаруживает неправильный результат.
5. Реализуйте получатели с одним `@DslMarker`, отдельное состояние каждого запуска и результат со списком расхождений.
6. Добавьте JSON-разбор и операции; переписывайте проверки по одной.
7. Проверьте несколько независимых расхождений и повторный вызов одного блока. Снимок первого результата не должен меняться.
8. В `docs/wont-compile.kt.txt` сохраните свой полный некомпилируемый пример, фактическую диагностику и объяснение. Исходник должен содержать package/import, модель ответа и вызывающую функцию, чтобы его можно было воспроизвести.
9. Выполните A–D из занятия 11 в той же ветке. Для варианта с `Class<T>` разрешены `T::class.java`, `Class.isInstance` и `Class.cast`. Обход членов классов и kotlin-reflect не нужны.
10. Сдайте ссылку на PR и ссылку на успешный пайплайн через карточку занятия 9. Точный срок указан в Academy.

## Критерии результата

Результат — sealed-иерархия или data-класс, не Boolean. Каждое расхождение содержит путь, ожидание и факт. Накопитель создаётся для отдельного запуска; наружу возвращается снимок списка. Собирайте все независимые расхождения без остановки на первом.

Для синтаксически неверного JSON проверяйте отсутствие каскада ошибок полей. Для отсутствующего поля получите отказ каждой заявленной операции над ним. Для повторяющихся операций сохраняйте порядок вызова; одна неудачная операция даёт одну запись.

Эквивалентность сравнивает именно `legacy(response)` с отсутствием расхождений у DSL. Дополнительно проверяйте содержание расхождений: одно только равенство флагов ошибки недостаточно.

`@DslMarker` ограничивает неявный выбор получателя. Явное обращение `this@check.status { ... }` допускается; подтвердите это отдельным компилируемым примером. Неверный пример храните с расширением `.txt`, вне компилируемых исходников.

## Самопроверка корпуса

Добавьте границы 199/200/299/300, пустой список значений, две записи одного заголовка с разным регистром, пустой JSON-объект, пропущенное поле и поле null, число и строку с одинаковыми символами, оба края Long и переполнение, экранированные кавычку и слеш, дубликат ключа с разными значениями. Для каждого случая сначала запишите ожидаемое поведение.

Для теста повторного вызова используйте неверный ответ и неизменяемые внешние данные. Сравните оба результата и сохранённую копию списка первого результата.
